# End-to-end tests drive the built app through an embedded WebDriver server, outside `make check`

The tests of the desktop app stop at its seams. Vitest with `mockIPC` proves how a screen draws a `Response`, and the Rust tests prove the commands through `procly-client`. Neither proves that the window, the embedded `procly` and a real Daemon work together: that the app starts a Daemon only when asked, that it notices a Daemon stopped from the CLI, that a Service started with `procly up` shows up with its port. The tickets of the app each need that proof live, so a thin end-to-end layer is built once and every ticket adds its flow to it.

The layer is WebdriverIO with `@wdio/tauri-service`, using its `embedded` driver provider. macOS has no WebDriver for WKWebView, so `tauri-driver` cannot serve it, and the CrabNebula driver needs a paid key there. The embedded provider runs a WebDriver server inside the app, through the `tauri-plugin-wdio-webdriver` crate, and works the same way on macOS and Linux.

- **Cargo feature:** the plugin is an optional dependency of `apps/desktop/src-tauri`, enabled by the feature `e2e`, which is off by default. A build without the feature has no WebDriver server and no extra dependency compiled. A build with it in release mode fails with a `compile_error!`, so the feature cannot reach a release by accident.
- **Build:** `make e2e` calls `make bundle` with `TAURI_ARGS="--features e2e ..."`, so the app embeds its sidecar like every bundle (`docs/rules/tauri.md`). macOS builds the `.app` and runs `Procly.app/Contents/MacOS/procly-desktop`. Linux has no `app` bundle type, so it builds with `--no-bundle` and runs `target/debug/procly-desktop`, where the sidecar sits beside it. Then it runs `wdio` from `apps/desktop`. The target is not part of `make check`, because it opens a window and takes minutes.
- **Isolation:** the runner creates temporary directories, sets `PROCLY_STATE_DIR` and `PROCLY_CONFIG_DIR` to them as the CLI test harness does, and picks a free loopback port for the WebDriver server. The service starts the app with that environment, so the app and the scenes reach the same Daemon, never the one of the developer. Each scene is set with the embedded `procly` (`up` in a repository the run created, `daemon stop`), never one found on the `PATH`. The runner stops the Daemon with `procly daemon stop` and removes the directories when it ends.
- **Driving the page:** the flows read and press the page through `browser.execute`. Measured on macOS with the embedded server, every new element lookup of `$` takes about 5 seconds and one flow lasted 4 minutes, while a script answers in a few milliseconds. The page is the one the developer sees.
- **One plugin only:** `tauri-plugin-wdio`, the bridge that adds `browser.tauri.execute()`, command mocking and log capture, is not taken. It needs `withGlobalTauri`, a permission in the capability of the window and an import in the frontend, all of which would then have to stay out of a release. The flows need none of it: the scenes are set with the CLI and the page is asserted on. The service only warns when the bridge is missing and fails inside `browser.tauri.*` alone, which the flows never call.
- **Versions:** `@wdio/tauri-service` is pinned to 1.5.1 and the crate to `=1.5.1`, upgraded together. The service requires Node 18.20 or later, and the Node of `.node-version` satisfies it. The service declares `webdriverio` ^9 as a peer and depends on 9.31.9, so the `@wdio` packages are pinned to 9.31, although the documentation site now shows v10. Moving to v10 waits for a release of the service that supports it.
- **Loopback listener:** ADR 0003 and the Tauri rules forbid a TCP or HTTP listener to reach the Daemon. The WebDriver server is not a path to the Daemon: it drives the window, it exists only in a build with the `e2e` feature, and no release carries it. The Daemon still listens on its Unix socket only.
- **CI:** a dedicated job of `ci.yml`, on macOS and on Linux under `xvfb-run`, runs `make e2e` on every pull request. A `paths` filter narrows the trigger if a run exceeds 10 minutes.
- **First flows:** the Daemon stopped from the CLI then started again through the sidecar, and a Service started by `procly up` appearing on the Overview with its port. The flows for live output, Restart and the release sheet arrive with their own tickets, in `apps/desktop/e2e/specs/`.

## Consequences

- A change of the window that a ticket must prove live adds a spec under `apps/desktop/e2e/specs/` and sets its scene with the CLI. It does not add a hook to the app.
- The runner opens the real window, so on a developer machine only one run drives the GUI at a time.
- WebdriverIO brings transitive packages with advisories. The `basic-ftp` and `serialize-javascript` ones are overridden to fixed releases in `package.json`, and the 2 of `extract-zip`, which no release fixes, are ignored by name in `security.yml` until one exists.
- The app writes its Seen failures under the data directory of the user, which the run does not redirect. The flows do not mark anything as Seen.
- Native surfaces, the menu bar, notifications and the Dock, are out of reach of WebDriver and stay in the manual checklist of the release.
